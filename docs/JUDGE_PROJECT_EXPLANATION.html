Autonomous AI DevOps Engineer

Detailed Project Explanation for Judges (Cloud + DevOps + MLOps + AWS)

Date: March 30, 2026

This project is a full-stack autonomous operations system that continuously watches logs, detects anomalies using ML + rule fallback, triggers cloud alerts, records remediation actions, and visualizes everything in a live operational dashboard. It is built as a practical, cost-aware student implementation of modern DevOps + AIOps concepts.

Frontend

Next.js App Router, React hooks, Tailwind CSS, live SSE consumption.

Backend

Node.js, Express, autonomous log watcher, AWS SDK v3 integrations.

ML

Python, Scikit-learn Isolation Forest, child-process inference in API pipeline.

1) Problem Statement and Objective

Traditional operations often detect incidents late and depend on manual triage. This project aims to demonstrate an autonomous flow where logs are ingested in real time, anomalies are identified quickly, alerts are propagated through cloud channels, and remediation decisions are tracked in a self-healing timeline.

  • Reduce mean time to detect (MTTD) through continuous monitoring.
  • Improve incident response consistency using deterministic remediation plans.
  • Provide explainable, demo-friendly visibility through a live dashboard.
  • Keep cloud cost low by using local-first ML with selective AWS services.

2) End-to-End Architecture

backend/logs/app.log -> fs.watch LogWatcher -> Decision Engine -> ML Predict (Python) -> Alert + Healing Workflow -> DynamoDB persistence -> SSE / API status -> Next.js dashboard \n(plus optional SNS email + S3 object storage)

Autonomous Processing Stages

  1. Log observation: File watcher detects only newly appended bytes to avoid reprocessing old content.
  2. Classification: Decision engine infers service, level, issue type, severity, and anomaly signal.
  3. ML inference: Python predictor returns anomaly indicators and confidence.
  4. Incident workflow: anomaly -> alert record + notification + remediation plan.
  5. State updates: rolling metrics and system health are recomputed and emitted.
  6. UI streaming: frontend receives events through Server-Sent Events (SSE) and renders timeline.

4) Backend Modules - Detailed Judge Walkthrough

4.1 Log Watcher (Autonomous Trigger)

The watcher monitors a configured log file and processes only new appended lines. This design mimics production tailing behavior and avoids duplicate ingestion.

  • Uses byte-offset tracking + partial-line buffering.
  • Builds log records and forwards each to the autonomous pipeline.
  • Emits real-time events for log, prediction, alert, healing, and status updates.

4.2 Decision Engine (Rule + Context Intelligence)

The decision engine classifies each log and computes severity/issue metadata, then combines rule-based anomaly signals with ML outputs for more robust detection.

  • Determines service and issue type from log semantics.
  • Maps severity from level and issue type.
  • Computes confidence and suggested actions for explainability.

4.3 Healing Service (What "Self-Healing" Means Here)

In this project, healing is an autonomous remediation workflow decision and execution record (restart/retry/recover) rather than direct cluster-level command execution.

  • Builds service-specific remediation plan (database/auth/payment/general).
  • Publishes or falls back alerts depending on AWS configuration and severity.
  • Stores anomaly, alert, and healing action in persistence.
  • Returns action payload that appears as "Issue healed" in dashboard timeline.
Viva-safe statement: "The prototype demonstrates autonomous remediation orchestration and traceable healing records; in production this step can be extended to invoke real orchestrator actions (for example ECS/Kubernetes restart APIs)."

4.4 Health Service (How "Issue Solved" Is Decided)

Health is recomputed from rolling windows. If critical anomalies exist, state is critical; if warning/error log load is high, state is degraded; otherwise healthy.

  • Inputs: recent logs + recent anomalies.
  • Output: health label + numeric factors for explainability.
  • This allows judges to see measurable criteria for recovery state changes.

6) AWS Services Used - How and Why (Detailed)

6.1 Amazon SNS Core Alert Channel

What it does: Sends anomaly notifications to subscribers (email, etc.).

How used: Backend publishes structured alert payloads for ERROR/CRITICAL severity paths.

Why used:

  • Managed pub/sub with minimal operational overhead.
  • Immediate notification during incidents.
  • Easy to demonstrate in viva (trigger anomaly -> receive alert).

6.2 Amazon S3 Durable Storage

What it does: Stores log objects and optionally model artifact.

How used: Log entries are uploaded under a logs prefix; model path can be synchronized from S3.

Why used:

  • Low-cost durable object retention.
  • Supports auditability and reproducibility.
  • Can decouple local runtime from model artifact lifecycle.

6.3 AWS DynamoDB State Persistence

What it does: Persists structured events (logs, anomalies, alerts, healing actions).

How used: Dedicated logical stores allow status, counts, and recent history queries.

Why used:

  • Serverless NoSQL with predictable scaling.
  • Good fit for append-heavy event records.
  • Simplifies summary metrics for dashboard and viva evidence.

6.4 AWS Lambda / API Gateway (Optional Extension)

The repository includes guidance for Lambda integration. Current implementation runs Express locally, but the same orchestration logic can be hosted serverlessly with API Gateway in front.

6.5 IAM Security Model

  • Least privilege policy for only required S3 and SNS actions.
  • Scoped ARNs for bucket prefixes and topic publishing.
  • Environment-based secret injection through backend .env for local mode.

8) Cost, Trade-offs, and Engineering Decisions

Decision Benefit Trade-off

Optional AWS mode Can run full demo even without active cloud account. Some production behavior simulated locally.
